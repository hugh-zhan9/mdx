## 这份文档回答什么

提案定的是方向和取舍，这份文档定的是**能照着写代码的契约**：模块怎么分、drawer 的每个字段写什么值、命令叫什么、请求响应长什么样、错误码是什么、旧数据怎么进来、面板每个 tab 从哪取数、测什么。

不回答的：具体交互稿与视觉（面板只给数据与动作契约）、执行排期（交给 plan2exec，本文最后一节给切片建议）。

上游 API 一律按 mempal 0.9.0 的公开签名写，引用位置见附录。**不改上游**：凡是需要改 mempal 才能做到的事，本文一律选择绕开或明确记为不做。

## 一、模块结构

现有 29 个平铺的 `src-tauri/src/memory_*.rs` 收成一个目录。这不是顺手重排，是因为文件边界本身要变——存储、检索、索引三层整个消失，剩下的部分按数据流向重新切。

```
src-tauri/src/memory/
├── mod.rs            对外门面；Tauri 命令体在 lib.rs 里只做薄包装
├── legacy.rs         今天的 memory.rs 原样搬进来（见下），P-009 删除
├── engine.rs         打开 palace.db、schema 兼容校验、wing 绑定、进程内单例与锁
├── embedder.rs       模型解析／下载／缺失时的硬失败
├── evidence.rs       写入路径：文件、会话转录、纯文本三个入口
├── knowledge.rs      蒸馏、门禁、采纳、降级
├── retrieval.rs      search / context / brief / recall
├── import_legacy.rs  旧 memory/ 目录一次性导入
├── models.rs         对外 DTO（serde，camelCase 出网）
├── config.rs         全局引擎配置 + 每工作区开关
├── capture/          会话捕获管道（沿用，改写落点）
│   ├── mod.rs        hooks / spool / queue 的现有逻辑
│   └── sources.rs    codex / claude-code / cursor 转录发现
├── agents.rs         agent 集成的安装、诊断、修复（沿用，改写文本与工具名）
└── wiki_promote.rs   结论 → `raw/promoted/` → LLM Wiki（沿用，改写渲染源）
```

**`memory.rs` 必须先让路。** 今天 `src-tauri/src/memory.rs`（830 行）与 `lib.rs:36` 的 `pub mod memory;` 占着 `memory` 这个模块路径，Rust 不允许 `memory.rs` 与 `memory/mod.rs` 同时存在（E0761）。做法是把它整体搬成 `memory/legacy.rs`，新的 `memory/mod.rs` 里 `mod legacy; pub use legacy::*;`——调用方写的 `crate::memory::memory_add` 照样解析，零 call-site 改动，新旧两套实现从此在同一个目录里各占各的文件。P-009 删 `legacy.rs` 和那行 re-export。

依赖边界：`memory/*` 是唯一允许 `use mempal_runtime::` 的地方。其它模块只能经 `memory::` 门面。加一条与编辑器同款的边界测试（`packages/mdx-editor` 已有先例）扫描源码，防止上游类型漏进 UI 层的 DTO。

Cargo 依赖加两个：

```toml
mempal-runtime = "0.9"                                              # 默认 features 含 model2vec
hf-hub = { version = "0.4", default-features = false, features = ["ureq"] }
```

上游只需要一个，因为 runtime 把需要的东西都 re-export 了：`core::db` 是整个 `mempal-store-sqlite`，`core::{anchor, types}` 是 `mempal-agent-memory` 的 `Drawer` / `derive_anchor_from_cwd` / 四个枚举，`embed` 是 `mempal-embed` 的 `Embedder` 与 `model2vec`。**不要单独写 `mempal-embed = "0.9"`**：它自己的 `default = []`，直接依赖反而拿不到 `Model2VecEmbedder`，得手写 `features = ["model2vec"]`；经由 runtime 的默认 feature 传递才是对的。

`hf-hub` 是我们自己下载模型要用的（feature 组合与 `model2vec-rs` 一致，不引入第二套 TLS）。`Model2VecEmbedder::new` 只会告诉你加载成功与否，不会把下载到的文件路径交出来，而我们需要把三件文件放进 `~/.mdx/models/<slug>/`。用 `ApiBuilder::with_cache_dir` 显式下载、拿到确切路径再原子移入，比去猜 HF 缓存的目录布局可靠。

## 二、依赖与工具链前置

这一节的三件事必须在写任何记忆代码之前完成，否则依赖装不进来。

| 项目 | 现状 | 目标 | 影响面 |
|---|---|---|---|
| rusqlite | 0.32.1（libsqlite3-sys 0.30.1） | 0.37（libsqlite3-sys 0.35.x） | `search_index.rs`、`memory_storage_sqlite.rs` 及测试，共 39 处 `rusqlite::` |
| MSRV | `rust-version = "1.77.2"` | `1.85`（上游 edition 2024） | `src-tauri/Cargo.toml`、开发环境说明；CI 用 `stable` 不受影响 |
| 二进制体积 | — | 增量实测后记录 | `mempal-runtime` 会带进 `clap`/`rmcp`/`jieba-rs`/`reqwest` |

`libsqlite3-sys` 声明 `links = "sqlite3"`，Cargo 不允许一个依赖图里出现两个版本，所以 rusqlite 升级是准入条件而不是可选项。这一步单独成片、单独验绿：升完 rusqlite 后现有测试必须全过，再动记忆。

## 三、存储与初始化

### 3.1 库位置与打开

```
~/.mdx/memory/
├── palace.db          Database::open(此路径)
├── wings.json         工作区绝对路径 → wing 的绑定表（我们自己的状态，不是上游 schema）
├── locks/             上游 per-source 咨询锁的落点
└── import-reports/    旧数据导入报告
```

`engine.rs` 提供进程内单例：一个 `Mutex<Database>`，所有命令排队通过。理由是全局单库现在会被多个窗口和 sidecar 同时写，而上游的咨询锁只覆盖 ingest 的 dedup+insert 临界区（且 Windows 上是空实现）。进程内串行化不解决跨进程竞争，那由 SQLite 自身的写锁兜底；我们要保证的是**同一进程里不出现交叉写**。

打开流程：

1. `Database::open(~/.mdx/memory/palace.db)`（会跑上游迁移）。
2. 读 `schema_version()`，与我们编译时锁定的期望值比较。不等则整个记忆功能进入 `schema_incompatible` 只读状态并在面板顶部说明——**不自动迁移、不静默降级**。
3. 校验 `embedding_dim()` 与当前模型维度一致；不一致时要求先 reindex（见 4.3）。

### 3.2 wing 与 room

wing 是项目边界，room 是项目内的分区。绑定规则：

- **wing** = `slug(工作区目录名) + "-" + sha256(绝对路径)[..6]`。带哈希是因为两个不同路径下的同名目录（`~/a/notes` 与 `~/b/notes`）必须是两个项目。
- 绑定写进 `wings.json`：`{ "/Users/x/notes": "notes-9f3c1a" }`。打开工作区时按绝对路径查表，查不到则新建并落盘。
- 工作区改名或移动 = 路径变了 = 查不到 = 会新建一个空 wing。面板发现「这个路径没有 wing，但库里有同名 wing」时，提供一次**显式重绑**（改 `wings.json` 的 key），不自动认亲。
- **room** = 文件相对工作区根的第一段目录（`raw`、`wiki`、`notes`…），根目录下的文件用 `root`；非文件来源（会话转录、人工确认）用 `session` 与 `review`。

### 3.3 并发与失败

| 情况 | 行为 |
|---|---|
| 库文件不可写 | 记忆整体报 `memory_unavailable` 并保持关闭，编辑器不受影响 |
| schema 版本不匹配 | 只读 + 明确提示，禁止写入 |
| 两个窗口同时写 | 进程内 Mutex 串行；跨进程由 SQLite 写锁 + 上游 `acquire_source_lock`（5s 超时）兜底，超时报 `memory_busy` |
| 写入中途失败 | 单条 drawer 是一次事务，失败即不留半条；批量导入按文件逐条提交，报告失败清单 |

## 四、嵌入模型

### 4.1 解析顺序

1. `~/.mdx/models/<model>/` 三件文件（`tokenizer.json`、`model.safetensors`、`config.json`）齐全 → 把该目录路径当作 model id 传给 `Model2VecEmbedder::new`，零网络。
2. 不齐全 → 记忆写入与语义检索一律不可用，返回 `embedding_model_missing`，附带体积与「现在下载」的动作。
3. 用户确认下载 → 设 `HF_HOME=~/.mdx/hf-cache`，按 repo id 走 hf-hub 下到临时目录，三件文件齐全后原子移入 `~/.mdx/models/<model>/`。

### 4.2 为什么不能降级成只用关键词

`ingest` 无条件调用 `embedder.embed()`，失败即整条写入失败。自己实现一个返回零向量的 `Embedder` 能骗过编译，但会往向量表里塞无意义向量并污染 RRF 融合后的排序。**不做**。没有模型就没有记忆写入，明确报错。

### 4.3 换模型 = 全量重嵌

向量维度记在库里。改模型（比如从 `potion-multilingual-128M` 降到 `potion-base-8M`）必须 `recreate_vectors_table(dim)` 并对 `all_active_drawers()` 全量重嵌。这是一个显式的、有进度和可中断提示的操作，不在启动时偷偷做。

## 五、领域模型：每个字段写什么

这是本文最需要精确的一张表。上游 `Drawer` 的字段很多，我们只用其中一个确定的子集，其余取默认。

| 产品概念 | memory_kind | domain | tier | status | field | anchor_kind / anchor_id | source_type | importance |
|---|---|---|---|---|---|---|---|---|
| 素材·文件（笔记、文档） | Evidence | Project | — | — | `general` | Repo / `repo://legacy`（上游写死，见 6.2） | Project | 0 |
| 素材·会话转录 | Evidence | Project | — | — | `general` | Worktree / `worktree://<工作区绝对路径>` | Conversation | 1 |
| 素材·人工确认记录 | Evidence | Project | — | — | `general` | Worktree / 同上 | Manual | 1 |
| 结论·候选 | Knowledge | Project | `qi` 或 `dao_ren` | `candidate` | `general` | Worktree / 由 `cwd` 派生 | Manual | 2 |
| 结论·已采纳 | Knowledge | Project | 同上 | `promoted` | 同上 | 同上 | Manual | 2 |
| 结论·已退役 | Knowledge | Project | 同上 | `demoted` / `retired` | 同上 | 同上 | Manual | 2 |

约定与理由：

- **tier 不上界面**。界面上是「具体」与「规律」，落到上游是 `qi` 与 `dao_ren`。`shu` 与 `dao_tian` 在 distill 阶段被上游拒绝，本产品建不出来（见文末偏差记录）。
- **domain 恒为 Project**。`Agent` / `Skill` / `Global` 是 coding agent 自我进化的维度，这个产品里没有对应物，留空比乱填好。
- **field 恒为 `general`**。上游的 field taxonomy 是只读建议，不强制；等真出现分领域检索的需求再启用，不提前造分类。
- **anchor 分两种，不是笔误**，原因见 6.2。外发布（`publish-anchor`，worktree → repo → global）第一期不做，跨工作区共享知识没有需求支撑。
- **importance 只用 0/1/2 三档**，分别是「批量素材」「有人参与的素材」「结论」。上游是 0-5，wake-up 按它排序；我们不做更细的分级，因为没有人会去调这个数。

### 5.1 素材内容的写法

会话转录直接存原文，交给上游的格式识别（Claude Code JSONL / Codex JSONL / ChatGPT / Slack / 纯文本）与 noise strip。人工确认记录用固定模板，让它在检索结果里也读得懂：

```
adoption confirmation
confirmed_at: 2026-08-17T09:12:44Z
confirmed_by: local-user
knowledge_drawer: kn_xxx
statement: PDF 导出统一走内嵌子集
reviewed_evidence: ev_aaa, ev_bbb
note: <用户可选填的一句话>
```

## 六、写入路径

三个入口，全部落在 `evidence.rs`。

| 入口 | 上游 API | 用途 |
|---|---|---|
| 文件 | `ingest::ingest_file_with_options` | 工作区里的 Markdown、导入旧数据 |
| 目录 | `ingest::ingest_dir_with_options` | 一次导入整个 `raw/` 或旧 `memory/` |
| 文本 | 自己构造 `Drawer` + `db.insert_drawer` + `db.insert_vector` | 会话转录、人工确认记录 |

第三个入口需要说明：**上游没有把「从字符串写一条 drawer」做成 runtime API**，那段逻辑长在 MCP server 里。我们不依赖 `mempal-mcp-server`（会把上游工具名带进用户的 agent），所以在 `evidence.rs` 里复刻同一套顺序，全部用公开 API：

1. `build_bootstrap_evidence_drawer_id(wing, room, content, &source_type, source_file)` 算身份——内容寻址，同内容同来源只会有一条。
2. `ingest::lock::acquire_source_lock(mempal_home, &drawer_id, 5s)` 进临界区。
3. `db.drawer_exists(&id)`；已存在直接返回（幂等）。
4. `Drawer::new_bootstrap_evidence(BootstrapEvidenceArgs{..})` 建条目，再覆盖 `anchor_kind` / `anchor_id` / `parent_anchor_id`（见 6.2）与 `normalize_version`。
5. `embedder.embed(&[content])` → `db.insert_drawer(&drawer)` → `db.insert_vector(&id, &vector)`。
6. 释放锁，返回 `drawer_id` 与 `lock_wait_ms`。

跳过的是上游 MCP 里的语义去重告警（`check_semantic_duplicate`）——它是 MCP 层的私有函数，我们够不着；内容寻址的身份已经挡住了完全相同的重复，近似重复留给用户判断。这是一个明确的能力缺口，不是遗漏。

### 6.2 为什么文件素材的 anchor 是 `repo://legacy`

`ingest_file_with_options` 内部用 `Drawer::new_bootstrap_evidence` 建条目，而这个构造函数的 anchor 是写死的 `(Repo, "repo://legacy")`（`anchor.rs:52`）——它不看 cwd，也没有参数可以传。想让文件素材带上 `worktree://` 锚点，只有三条路：改上游（不做）、绕开 `ingest_file` 自己拼装（要复刻 normalize + chunk + 身份计算）、或者接受它。

**接受它**，因为它不影响检索：上下文组装的锚点链是 `worktree://<path> → repo://<parent> → repo://legacy`，最后那条正是给 P12 之前的老库留的兜底（`context.rs:384`），文件素材照样进得来。

但**我们自己写的条目要显式覆盖 anchor**：用 `anchor::derive_anchor_from_cwd(工作区根)` 得到 `worktree://<绝对路径>`，写进 Drawer 再入库。理由是 `list_projects()` 的项目路径取自「最近一条 worktree 锚点」，全是 legacy 锚点的 wing 会报 `path: null`，概览页显示不出项目在哪，跨项目接续也就无从谈起。会话转录和人工确认记录每个活跃工作区都会有，足够让这条路径始终有值。

副作用是同一个 wing 里锚点不齐：会话与结论在 worktree 层，文件素材在 legacy 层。组装上下文时前者先出现——这个顺序反而是想要的，当下会话的上下文本来就该排在陈年文件前面。

### 6.1 捕获管道

`capture/` 保留现有的 hook → spool → queue 结构（hook 只落盘不做重活，后台消费），只把终点从「写 Markdown + 索引」改成「写 evidence drawer」。捕获开关默认关闭，与今天一致。

安全面：素材一旦捕获就在库里，只能事后 soft-delete，这是抛弃 inbox 的直接后果。对应措施两条，都必须实现：

- **捕获前的来源白名单**：只捕获用户显式勾选过的 agent 与目录，默认空。
- **面板上的一键删除**：`db.soft_delete_drawer` + 一个显式的「彻底清除」入口（`purge_deleted`）。

## 七、提升路径：候选 → 采纳

按 2026-08-17 裁决实现，一次点击过门槛。

```
素材（若干条 evidence）
   │  蒸馏：用户在面板上选中素材 → 写 statement + 正文
   ▼
prepare_distill(DistillRequest{ statement, content, tier, supporting_refs: <选中的素材 id>, wing, room,
                                domain: project, field: general, cwd, importance: 2, dry_run })
   │  → DistillPlan::Create(prepared) → commit_distill(...)
   ▼
结论（candidate，支持证据已自动挂上）
   │  采纳：写一条人工确认 evidence（见 5.1）→ 得到 confirm_id
   ▼
promote_knowledge(PromoteRequest{ drawer_id, status: "promoted", verification_refs: vec![confirm_id],
                                  reason: <用户填或默认「面板采纳」>, reviewer: Some(local-user),
                                  allow_counterexamples: false, enforce_gate: true })
   ▼
结论（promoted）── 从此进入 context / brief
```

规则：

- `enforce_gate` 恒为 `true`。门禁失败时把 `GateReport.reasons` 原样显示，不改写、不吞掉。
- `allow_counterexamples` 恒为 `false`。有反例就是提不上去。
- **不做批量采纳**。一次一条，每条留一条确认记录。批量会让本就退化成记账的门禁再降一档。
- 降级走 `demote_knowledge`，`status` 取 `demoted`（还可能回来）或 `retired`（作废），`evidence_refs` 必填——要退役一条结论，得说明依据。

### 7.1 反例证据从哪来

今天没有任何入口会产生 counterexample_refs，等于门禁的另一半永远用不上。第一期补一个最小入口：结论详情里的「记录一条反例」——写一条 evidence 并挂到该结论的 `counterexample_refs`。挂上之后该结论会被门禁挡住，已 promoted 的则提示可降级。不做自动检测。

## 八、读取路径

| 命令 | 上游 API | 返回 |
|---|---|---|
| `memory_search` | `search::search_with_options` | 命中列表，每条带 `drawer_id`、`source_file`、`wing/room`、结构化 signals |
| `memory_context` | `context::assemble_context` | 按 `dao_tian → dao_ren → shu → qi` 排序的上下文包 + 证据引用 |
| `memory_brief` | `brief::assemble_brief` | 确定性摘要：事实、证据、不确定项、下一步 |
| `memory_recall` | 上面三者的组合 | agent 的单一入口 |

`memory_recall` 这个名字保留。它不是被删概念的别名——「给我这个任务需要的上下文」这件事没有变，变的是实现。新的返回体：

```jsonc
{
  "context": { "items": [...], "anchors": [...] },   // assemble_context
  "brief": { "summary": "...", "keyFacts": [...] },  // assemble_brief
  "hits": [ { "drawerId": "...", "sourceFile": "...", "snippet": "...", "score": 0.0 } ],
  "truncated": false
}
```

删掉的字段：`working`（概念已抛弃）、`threads`（会话现在就是素材，走 `hits`）。

参数默认值：`context.max_items = 12`、`dao_tian_limit = 1`、`include_cards = false`（Phase-2 卡片本期不用）、`include_evidence = true`、`search.top_k = 8`。全部可在全局配置里改。

## 十、旧数据导入

两步，与用户已经熟悉的「预检 / 执行」同一个模式。

**预检**（`memory_legacy_import_dry_run`）扫描工作区，报告：

```jsonc
{
  "memories": 128,     // memory/memories/**.md → 将作为素材导入
  "threads": 34,       // memory/threads/**.md  → 将作为素材导入
  "inbox": 12,         // 不导入（未确认的自动产物）
  "working": true,     // 不导入（易失内容）
  "estimatedBytes": 2411032,
  "modelReady": true
}
```

**执行**（`memory_legacy_import`）逐文件 `ingest_file_with_options`，wing 取该工作区，room 取 `legacy/<原子目录>`，`source_type = Project`。内容寻址保证重跑幂等。结束写一份报告到 `~/.mdx/memory/import-reports/<时间戳>.json`，包含成功数、跳过数、失败文件与原因。

旧目录**不动**：`<workspace>/memory/**` 原地保留只读，回退 = 换回旧版本应用。

导入结果是**素材，不是结论**。报告末尾必须说清这一句，并附一个「按导入时间排序的前 N 条」列表，方便用户挑值得蒸馏的内容。这是换模型最直接的用户可感代价，藏起来只会让人以为记忆丢了。

## 实现与设计的偏差

写代码时撞上的、设计当时不知道的事，逐条记下来，避免后来的人以为是实现走样。

**结论只有两档，`shu` 建不出来。** `prepare_distill` 只接受 `qi` 与 `dao_ren`，明确拒绝 `shu` 与 `dao_tian`（`knowledge_distill.rs:249`）。第五节原写「一律落 shu 或 qi」，改为：`concrete`→`qi`，`pattern`→`dao_ren`（门槛 ≥2 条支持证据）。

**退役必须给理由类型。** 上游只收 `contradicted / obsolete / superseded / out_of_scope / unsafe`（`knowledge_lifecycle.rs:223`）。原设计没提，现在作为枚举暴露到界面——这本来就该记进审计。

**多了一个直接依赖 `hf-hub`。** `Model2VecEmbedder::new` 不返回下载到的文件路径，而我们要把三件文件放进 `~/.mdx/models/<slug>/`。用 `ApiBuilder::with_cache_dir` 显式下载拿确切路径，比猜 HF 缓存布局可靠。feature 组合与 `model2vec-rs` 一致，不引第二套 TLS。

**`memory.rs` 先搬成 `memory/legacy.rs`。** 与 `memory/mod.rs` 不能共存（E0761）。搬家 + `pub use legacy::*;` 让调用方一行不改。

**`rusqlite` 0.32 → 0.37 没有 API 适配工作。** 设计预估 39 处调用要改，实际一处未改，整个 diff 是两行版本号。

**`ingest_file` 加了 room 覆盖参数。** 旧数据导入要把文件放进 `legacy/<子目录>`，而 `room_for` 只返回单段。加参数而不是让导入绕过共享入口，否则写入路径会有两份。

**素材的 `source_type` 交给上游按格式判定**，不强制 `Project`。一个真是 Claude JSONL 的文件被识别成 `Conversation` 更准确。

**备份包的错误码是 `bundle_export_failed` / `bundle_import_failed`**，沿用旧实现的词汇；第十二节的表当时没有这两条，现已补上。
