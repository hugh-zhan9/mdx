# 记忆引擎：依赖 mempal 的 library crate，数据留在 `~/.mdx/`，模型首次使用才下载

Author(s): Claude（与 hugh-zhan9 讨论）
Last updated: 2026-08-17
Status: Draft — 待评审，未动代码
Source requirements: 2026-08-17 会话中的口头需求与三条约束——「不想还叫 mempal」「担心版本分叉」「数据保存到 `~/.mdx/` 下」「构建时不下载模型，初次使用才下载」
Support lenses: architecture-designer（边界、失败模式、可运维性）、sql-style（存储与迁移）

## 摘要

采用 mempal 的 **library crate 作为 Cargo 依赖**，不复制代码、不 fork。数据库落在 `~/.mdx/memory/`，嵌入模型落在 `~/.mdx/models/`，产品界面上不出现 "mempal" 字样。

你的三个问题都有明确答案，且都不需要改造上游：

| 问题 | 答案 | 依据 |
|---|---|---|
| 数据能否放 `~/.mdx/` | **能** | `Database::open(path: &Path)`（`mempal-store-sqlite/src/lib.rs:180`）；runtime 的 API 普遍接受 `mempal_home: &Path` 参数，`~/.mempal` 只是缺省值 |
| 构建时是否下载模型 | **本来就不下载** | `model2vec.rs` 全文 1.6 KB，整个 crate 36 KB，没有 `include_bytes!`；模型经 `StaticModel::from_pretrained` 在**首次构造 embedder 时**才取 |
| 模型能否放 `~/.mdx/` | **能** | `from_pretrained` 先判 `if base.exists()` 走本地目录，否则才走 HF Hub |
| 版本分叉 | **不会** | 依赖 crates.io 版本，`cargo update` 即跟进。会分叉的是复制或 fork，本方案两者都不做 |

代价必须说清：**这是替换而不是叠加**。现有 `src-tauri/src/memory*.rs`（十余个文件）会被取代，两套 schema 之间需要一次性迁移；构建体积和首次编译时间会明显上升。

## 背景与证据

mempal 不是一个单体二进制。`ref/mempal/crates/` 下是 7 个默认可发布的 library crate：

| crate | 作用 |
|---|---|
| `mempal-runtime` | 核心逻辑，20+ 公开模块（`search`、`ingest`、`context`、`knowledge_*`、`doctor`…） |
| `mempal-store-sqlite` | SQLite + sqlite-vec 存储 |
| `mempal-search-core` | BM25 + 向量，RRF 融合 |
| `mempal-embed` | 嵌入后端（model2vec / onnx 两个 feature） |
| `mempal-mcp-protocol`、`mempal-mcp-server` | MCP 协议与服务端 |
| `mempal-agent-memory` | agent 记忆语义 |

顶层 `mempal` crate 只是 `[[bin]]`。**这意味着可以按需只依赖需要的部分**，不必把 CLI 和 MCP server 一起拖进来。

关于命名：crate 名与产品名是两件无关的事。本项目已经在用 SQLite、ProseMirror、KaTeX、Prism，产品界面一个字都没提过它们。记忆功能在 UI 上叫什么（现在叫「记忆」）完全由我们定。

## 目标与非目标

### 目标

- 记忆能力（混合检索、知识图谱、跨项目关联）由上游维护，我们不再自研检索与存储。
- 数据、模型、缓存全部在 `~/.mdx/` 之下，与 drafts、assets、themes 同一个约定。
- 构建产物不含模型；用户不启用记忆功能就永远不下载。
- 升级路径是 `cargo update`，不是手工合并。
- 产品界面不出现上游名称。

### 非目标

- **不 fork、不 vendor、不改上游代码。** 一旦需要改上游，先提 issue/PR；本地补丁只作为临时手段并记录到期时间。
- **不做双后端共存。** 两套记忆实现同时在线会产生「哪份是真的」这个无法回答的问题。
- **不迁移 MCP server。** 现有 `mdx-mcp` sidecar 的对外协议不变，本提案只换它背后的存储与检索。
- **不在本提案内重做记忆 UI。** UI 已在本次会话单独处理。

## 三个方案与取舍

| 方案 | 形态 | 版本分叉 | 数据/模型位置可控 | 构建成本 | 结论 |
|---|---|---|---|---|---|
| **A. Cargo library 依赖** | `mempal-runtime = "0.9"` 等，直接调 API | 无（`cargo update`） | 完全可控（路径参数） | 首编译显著变长，产物变大 | **推荐** |
| B. sidecar 二进制 | 打包 `mempal` 可执行文件，走 CLI/stdio | 无 | 可控（`--home` 之类参数） | 产物含完整二进制，进程管理复杂 | 备选 |
| C. MCP 协议对接 | 把 mempal 当外部 MCP server | 无（用户自己装） | 用户自己定 | 最低 | 拒绝：需用户自行安装并保持运行，记忆变成"可能不在"的功能 |
| D. 复制/fork 代码 | 抄进 `src-tauri/` 或 fork 后改名 | **严重** | 完全可控 | 中 | 拒绝：正是你担心的分叉 |

选 A 的理由：只有 library 依赖能同时做到"升级只需改版本号"和"路径与命名完全由我们决定"。B 也不分叉，但把记忆变成需要管生命周期的子进程，而它是一个随应用启停的本地能力，多一个进程只多一处会挂的地方。

A 的代价是编译期。`sqlite-vec` 与 `model2vec-rs` 都不轻，首次 `cargo build` 会明显变慢。这个成本落在开发和 CI，不落在用户运行时。

## 数据与模型落位

```
~/.mdx/
├── assets/            （既有）
├── drafts/            （既有）
├── themes/            （既有，本次会话新增）
├── memory/
│   └── palace.db      ← Database::open(此路径)
└── models/
    └── potion-multilingual-128M/   ← 首次使用时落盘
```

**数据库**：所有入口都从我们自己的 `mdx_home_dir()?.join("memory")` 出发，与 `assets.rs:612` 同一个函数。上游的 `~/.mempal` 缺省值永远不被触及。

**模型**：`from_pretrained` 的本地分支要求目录下同时存在 `tokenizer.json`、`model.safetensors`、`config.json`。所以流程是：

1. 首次需要 embedder 时，检查 `~/.mdx/models/<model>/` 是否齐全。
2. 齐全 → 传本地路径，零网络。
3. 不齐全 → 设 `HF_HOME=~/.mdx/hf-cache` 后按 repo id 调用，让 hf-hub 下载；完成后校验三件文件齐全。

**下载必须是用户显式触发的**。不是"打开记忆页面就静默下载几百 MB"，而是首次执行需要语义检索的操作时，先告知体积并征得同意；只用关键词检索（BM25）不需要模型。这一条是产品行为，不是实现细节——它决定了一个离线用户是否会看到不明来源的网络请求。

## 迁移

现有记忆数据在 `~/.mdx/` 下由自研实现管理，与 mempal 的 schema 不同。**迁移是一次性、可回退的**：

1. 旧数据不删。新库建在 `memory/palace.db`，旧数据原地保留为 `memory-legacy/`。
2. 迁移是显式动作（设置里的按钮），有预检：先报告将迁移多少条、哪些字段无法对应，再执行。这与现有 `memory-settings-section.tsx` 里 SQLite→PostgreSQL 的「迁移预检 / 开始迁移」两步是同一个模式，用户已经熟悉。
3. 无法对应的字段**不静默丢弃**，写入迁移报告。
4. 回退 = 切回旧版本应用，旧数据仍在原处。

**字段对不上的地方需要在详细设计里逐项列出**，这是本提案最大的未知：现有实现有 inbox（待确认候选）、working context（工作上下文）、projection（Markdown 投影）等概念，mempal 有 wing/room、knowledge card、tunnel 等概念，两边不是一对一。

## 边界场景

| 场景 | 处理 |
|---|---|
| 用户从不启用记忆 | 不建库、不下模型、不发请求。依赖只增加二进制体积 |
| 离线环境首次语义检索 | 明确报错说明需要下载模型，并指出可先用关键词检索；不静默失败 |
| 下载中途断网 | 不留半个模型：先下到临时目录，三件文件齐全再原子移入 |
| 模型目录被手动删除 | 下次使用时重新走下载流程，不崩 |
| `~/.mdx/memory/` 不可写 | 记忆功能整体报错并保持关闭，编辑器不受影响 |
| 上游 breaking change | 依赖锁在 `Cargo.lock`；升级是显式动作，跟着上游 CHANGELOG 走 |
| 两个窗口同时写 | SQLite 单文件并发由上游负责；我们不额外加锁，但要在详细设计里确认它的并发保证 |
| 旧数据迁移一半失败 | 新库丢弃重建，旧数据未动，报告失败原因 |

## 待决问题

1. **功能对齐**：现有 inbox / working context / projection 在 mempal 里的对应物是什么？有没有对不上的？**这一项阻塞详细设计**，因为它决定迁移是"换引擎"还是"换产品"。
2. **产品命名**：记忆功能在 UI 上继续叫「记忆」即可，但数据目录、迁移报告、诊断输出里要不要出现上游名称？我倾向内部诊断信息保留（便于排查和向上游报 issue），面向用户的文案不出现。
3. **模型体积与默认值**：`potion-multilingual-128M` 的实际下载体积需要实测确认。若过大，是否默认降级到 `potion-base-8M`（256 维）？
4. **是否需要语义检索**：如果只用 BM25 关键词检索就够，可以完全不引入 `mempal-embed`，构建成本和网络问题一起消失。这个选择应该由实际检索质量决定，而不是由实现便利决定。

## 详细设计交接

**建议先评审本提案。** 待决问题 1 决定迁移的性质，4 决定依赖范围，两者都会改变详细设计的内容。

评审通过后，以下决定作为约束固定：

- 依赖 crates.io 的 library crate，不 fork、不 vendor、不改上游。
- 数据 `~/.mdx/memory/`、模型 `~/.mdx/models/`，全部经我们自己的 home 解析函数。
- 构建产物不含模型；下载由用户显式确认，且只在需要语义检索时。
- 迁移是显式两步（预检 + 执行），旧数据原地保留，可回退。
- 产品界面不出现上游名称。
- 不做双后端共存。
