# 记忆引擎：抛弃自研记忆模型，改用 mempal 的「证据／知识」两层模型

Author(s): Claude（与 hugh-zhan9 讨论）
Last updated: 2026-08-17
Status: 已实施 — 见 [详细设计.md](./详细设计.md) 与 docs/loopx/plans/2026-08-17-memory-engine-adoption.md
Source requirements: 2026-08-17 会话。第一轮四条约束——「不想还叫 mempal」「担心版本分叉」「数据保存到 `~/.mdx/` 下」「构建时不下载模型，初次使用才下载」；第二轮裁决——「现有的 inbox（待确认）、working context、projection 直接抛弃，基于 mempal 重新设计」。
Support lenses: architecture-designer（边界、失败模式、可运维性）、sql-style（存储与迁移）

## 摘要

第一版提案讲的是换引擎：底层换成 mempal，上层产品概念不动。它卡在一个问题上——inbox、working context、projection 在 mempal 里找不到对应物，迁移到底是「换引擎」还是「换产品」没有答案。

裁决把这个问题解掉了：这三个概念不映射，直接删。于是提案性质变了，**这不是换引擎，是换记忆模型**。mempal 的模型是两层——底下是证据（evidence drawer，原文入库，带出处），上面是知识（knowledge drawer，有分级、有状态、有提升门禁）。我们现有的一套概念是另一个模型：一条记忆写进 Markdown 文件，自动蒸馏出的候选先进 inbox 等人确认，当前关注手写在 `working.md` 里。两个模型没有平移关系，所以按裁决重做。

第一版关于依赖形态的结论仍然成立，不重复论证：

| 结论 | 状态 |
|---|---|
| 依赖 crates.io 的 library crate，不 fork、不 vendor、不改上游 | 不变 |
| 数据落 `~/.mdx/memory/`、模型落 `~/.mdx/models/`，都走我们自己的 home 解析函数 | 不变 |
| 构建产物不含模型，首次使用才下载 | 不变 |
| 产品界面不出现上游名称 | 不变 |

这一版新增了三件第一版没有说的事：

1. **依赖 mempal 会强制我们升 rusqlite 和 Rust 工具链**，这是 Cargo 的硬约束，不是权衡（见「依赖与构建」）。
2. **写入路径无条件需要 embedder**，「只用关键词检索所以不引入嵌入模型」这条退路不存在（见「已决问题」）。
3. **删掉的不止三个概念**：PostgreSQL 后端、自研索引、Markdown 投影、CLI/MCP 的一批工具名，都跟着一起走。

## 本轮裁决

> 现有的 inbox（待确认）、working context、projection 直接抛弃，基于 mempal 重新设计。

它决定了：迁移不做字段映射；这三块的实现代码和对外命令直接删；产品概念表按 mempal 重画。

它没有决定的三件事——PostgreSQL 后端去留、提升门禁怎么落地、界面上用什么词——在同一天的后续讨论里定了前两件，见「已决问题」；界面词汇留在「待决问题」。

## 新模型：证据在下，知识在上

mempal 的核心是一条单向的加工链，每一段都有独立的存储形态和治理规则：

```
原始素材（会话、文档、笔记）
   │  ingest：切块 + 原文入库 + FTS5 + 向量
   ▼
evidence drawer ── 可检索、带 drawer_id 与 source_file 出处、可 soft-delete
   │  distill：从若干 evidence 引用生成一条候选结论
   ▼
knowledge drawer（candidate）
   │  gate：按证据数量与角色判定是否够格
   │  promote：显式动作，写 append-only 审计事件
   ▼
knowledge drawer（promoted / canonical）── 才会进入运行时上下文
```

两个正交的维度落在 knowledge 上：

- **分级（tier）**：`qi`（具体工具与用法）、`shu`（可复用方法）、`dao_ren`（领域内稳定规律）、`dao_tian`（跨领域公理）。运行时组装上下文时按 `dao_tian → dao_ren → shu → qi` 排序，`dao_tian` 默认限 1 条。
- **状态（status）**：`candidate / promoted / canonical / demoted / retired`（`mempal-store-sqlite/src/lib.rs:2371`）。

检索面也不止一个：`search` 是混合检索（BM25 + 向量 + RRF），`context` 是按分级组装的上下文包，`brief` 是确定性的「事实 + 出处 + 不确定项 + 下一步」摘要，`projects` / `resume` 让你从任意目录接续另一个项目。

### 概念对照

| 现有概念 | 处置 | 新载体 |
|---|---|---|
| `memory/inbox/`（待确认候选） | **抛弃** | 不再有「入库前的等待区」；把关移到 knowledge 的 `candidate → promoted` |
| `memory/working.md`（工作上下文） | **抛弃** | `context` 运行时组装 + `brief` 摘要，机器算出来，不是人写出来 |
| `memory/memories/**.md`（Markdown 投影） | **抛弃** | `palace.db` 是唯一真相；可见性靠检索结果带 `drawer_id` + `source_file` |
| 长期记忆（`memory add/list/archive`） | 重新解释 | knowledge drawer；`archive` 变成 `demote` / `retire` |
| 会话线程（`memory/threads/`） | 重新解释 | evidence drawer；mempal 原生识别 Claude Code / Codex / ChatGPT / Slack 四种转录格式 |
| 自动蒸馏（LLM 抽候选） | 重新解释 | `distill` 是确定性的：从已存在的 evidence 引用建候选，不调 LLM（`knowledge_distill.rs:61`） |
| 自研索引 `.mdx/search.sqlite` | **抛弃** | FTS5 + sqlite-vec + RRF，索引与数据同库 |
| SQLite / PostgreSQL 双后端与迁移 | **抛弃** | mempal 只有 SQLite |
| 工作区内的 `memory/` 目录 | **抛弃** | 全局 `~/.mdx/memory/palace.db`，按 wing 区分项目 |
| 知识图谱、跨项目隧道 | 新增 | 三元组（带时态有效期）、同名 room 跨 wing 自动关联 |

## 抛弃的三件事，职责去了哪里

删掉概念不等于删掉它承担的职责。三件事各自的去处，以及各自丢掉的东西：

### 待确认 → 提升门禁

旧模型里，agent 拿不准的东西写进 inbox，人点「接受」它才成为记忆。把关发生在**入库前**。

新模型里，素材直接进证据层，不需要谁批准；把关发生在**提升前**：一条候选结论要变成 agent 会读到的知识，得过 gate。gate 不看人的判断，看证据（`knowledge_gate.rs:180`）：

| 目标 | 支持证据 | 验证证据 | 教学证据 | 需要 reviewer | 有反例就挡 |
|---|---|---|---|---|---|
| `qi` / `shu` → promoted | ≥1 | ≥1 | 0 | 否 | 是 |
| `dao_ren` → promoted | ≥2 | ≥1 | 0 | 否 | 是 |
| `dao_tian` → canonical | ≥3 | ≥2 | ≥1 | 是 | 是 |

**丢掉的是**：「这条信息敏感／不确定，先别存」这个动作没有了。素材一旦被捕获就在库里，只能事后 soft-delete。agent 指令里「不要写机密」这句话从一条可以兜底的产品规则，退化成一条只能靠 agent 自觉遵守的约定。这是真实的安全面变化，必须在详细设计里给出对应措施（至少：捕获前的路径／来源白名单，和面板上一键 soft-delete + purge）。

**门槛调不了**：`promotion_policy()` 是只读的（`knowledge_gate.rs:45`），阈值写死在上游。挂证据这件事每条结论都得做一次，指望人手工做，结果就是没人做，候选永远停在 candidate，`context` 和 `brief` 拿不出东西，知识层等于不存在。

**裁决（2026-08-17）：系统自动挂证据，人一键采纳。** 落地流程：

1. 蒸馏产生候选结论时，把它引用的来源素材自动记为**支持证据**——这些引用本来就是 distill 的输入（`knowledge_distill.rs:61`），不是额外编造的。
2. 人在面板上点「采纳」时，先写一条记录本次人工确认的证据（谁、什么时候、确认的是哪条结论），再把它挂为**验证证据**。上游要求引用指向真实存在的 evidence drawer，这条记录满足要求，且它确实是一次可追溯的验证行为。
3. 两条齐了就调 gate，通过则 promote，失败把 gate 报告里的 reasons 原样显示出来。

**这个选择的代价，明说**：门禁不再起过滤作用，退化成记账。真正拦住东西的只剩「有没有人点过采纳」和「有没有挂反例」。换句话说，被抛弃的 inbox 那个人工确认动作以另一种形式回来了——位置从入库前挪到了提升前，区别是这次留下了出处和审计事件（`knowledge_events` 是 append-only）。

由此产生两条详细设计必须回答的问题：反例证据谁来挂（今天没有任何入口会产生 counterexample），以及批量采纳要不要允许（允许就等于一次点击提升一批，记账的意义再降一档；本提案倾向不允许）。

### 工作上下文 → 运行时组装的上下文包

旧模型里 `working.md` 是一个人和 agent 都能写的自由文本文件，session 启动先读它。

新模型里没有这个文件。`context` 每次按当前任务、按 `dao_tian → dao_ren → shu → qi`、按 `worktree → repo → global` 的锚点顺序现算一份（`context.rs:149`），`brief` 再压成带出处的摘要（`brief.rs:108`）。

**丢掉的是**：手写「我现在在干什么」的位置。这是个真实的功能损失——机器组装的上下文来自已经沉淀的知识，而「我今天要改的是这个 bug」这类临时意图并没有沉淀过。详细设计要回答：这类临时意图是作为一条 `qi` 级证据写进去，还是承认它不属于记忆层。我倾向后者，理由是它本来就是易失的，塞进持久化记忆只会污染检索。

### Markdown 投影 → 单一真相 + 引用

旧模型里每条记忆都会写一份 `.md` 到工作区，可以在编辑器里打开、可以 git 提交、可以被 wiki 链接。

新模型里只有 `palace.db`。

**丢掉的是**：记忆不再是「文档」。对一个 Markdown 编辑器来说这是最不舒服的一条——用户不能再直接编辑一条记忆，不能 diff，不能把记忆随仓库一起提交给同事。补偿只有两个，都要在详细设计里落实：面板里的只读查看必须做到可读（含出处跳转到源文件），以及导出功能必须能把库导回一堆 Markdown。

顺带保住一条既有链路：`memory promote` 把内容复制到 `raw/promoted/` 再可选 ingest 进 LLM Wiki（`docs/loopx/specs/memory.md:251`）。这是 Memory 与 Wiki 唯一的交叉点，不在抛弃范围内。改动是：渲染的源从 Markdown 文件变成 drawer / card。

## 产品词汇：不把 dao/shu/qi 抬到界面上

mempal 的词汇（wing、room、drawer、dao_tian、qi、canonical）是给 coding agent 的治理语言，不是给写 Markdown 的人看的。产品界面维持两个词：

| 界面词 | 底层 | 说明 |
|---|---|---|
| 素材 | evidence drawer | 会话、文档、笔记，原文可查 |
| 结论 | knowledge drawer | 有状态：候选 / 已采纳 / 已退役 |

分级不暴露给用户：用户和 agent 新建的结论一律落 `shu` 或 `qi`；`dao_ren` 需要显式操作；`dao_tian` 我们不产生，只在库里已有时只读展示。`field` 默认 `general`。诊断信息和日志里保留上游原名，方便排查和向上游提 issue——这与第一版待决问题 2 的倾向一致，现在把它定下来。

第一版写了「不在本提案内重做记忆 UI」。这条要修正：视觉不重做，但 tab 结构必须跟着模型走，因为其中两个 tab 的概念被删了。现有七个 tab（`features/memory/lib/memory-panel-state.ts:19`）的处置：

| 现有 tab | 处置 |
|---|---|
| 概览 | 保留，内容换成库状态：wing/room/drawer 计数、schema 版本、嵌入模型状态 |
| Agent 集成 | 保留，安装的技能文本与工具名全部重写 |
| 会话 | 改名「素材」，列 evidence，来源不限于会话 |
| 长期记忆 | 改名「结论」，按状态分组，合并原「待确认」 |
| 待确认 | **删除**，其角色由「结论」里的候选态承担 |
| 工作上下文 | 改成只读的「本次上下文」预览，展示 agent 实际会拿到什么；不可编辑 |

具体交互稿不在本提案内。

## 数据落位：一个全局库，按工作区分 wing

```
~/.mdx/
├── assets/            （既有）
├── drafts/            （既有）
├── themes/            （既有）
├── memory/
│   └── palace.db      ← Database::open(此路径)
└── models/
    └── <嵌入模型>/     ← 首次使用时落盘
```

这是本提案里除概念替换外最大的一处变化，值得单独说清楚：**记忆从「跟着仓库走」变成「跟着人走」**。今天记忆在工作区里（`<workspace>/memory/**.md` + `<workspace>/.mdx/memory.sqlite`），换台机器 clone 一下仓库记忆就在；以后记忆在用户目录的单一库里，换台机器就没有，只能靠导出／导入。

选全局单库而不是每工作区一个库，理由是跨项目能力只在单库里成立：隧道要在同一个库里发现同名 room，`projects` / `resume`（`projects.rs:82`、`:152`）要在同一个库里列出所有项目。拆成每工作区一个库，等于把 mempal 一半的价值扔掉，那还不如不换。

两条相关决定：

- **不共用用户已有的 `~/.mempal/palace.db`。** schema 版本由我们的 `Cargo.lock` 锁定，共用会让我们的 `cargo update` 影响用户命令行工具里的数据。两套库互不干扰。
- **wing 与工作区的绑定按绝对路径记录。** 工作区改名或移动后 wing 不自动跟随，需要一次显式的重新绑定动作，否则同一个项目会分裂成两个 wing。

模型落位与下载流程沿用第一版：先查 `~/.mdx/models/<model>/` 三件文件是否齐全，齐全走本地零网络，不齐全设 `HF_HOME=~/.mdx/hf-cache` 后下载，下到临时目录校验齐全再原子移入。

## 依赖与构建：三个硬约束

第一版只说了「首次编译会变慢」。实际约束比这个硬。

**一、rusqlite 必须从 0.32 升到 0.37。** 这不是可选项。`libsqlite3-sys` 声明了 `links = "sqlite3"`，Cargo 不允许同一个依赖图里出现两个链接同一个本地库的包。我们现在锁的是 rusqlite 0.32.1 / libsqlite3-sys 0.30.1（`src-tauri/Cargo.lock:2561`），mempal 要 rusqlite 0.37（libsqlite3-sys 0.35.x）。要么全升，要么依赖不进来。影响面是 `search_index.rs`、`memory_storage_sqlite.rs` 和相关测试，共 39 处 `rusqlite::` 调用。

**二、Rust 版本从 1.77.2 升到 ≥1.85。** mempal 全部 crate 是 edition 2024、`rust-version = "1.85"`。我们的 `src-tauri/Cargo.toml:16` 写的是 1.77.2。我们自己的 crate 可以继续留在 edition 2021，但工具链底线要抬。CI 用的是 `dtolnay/rust-toolchain@stable`，不受影响；受影响的是本地开发环境和 MSRV 承诺。

**三、`mempal-runtime` 会把它的 CLI 和 MCP 依赖一起拖进来。** 它的 `[dependencies]` 里有 `clap`、`rmcp`、`jieba-rs`、`tokio`、`reqwest`（经 `mempal-embed`）。我们既不用它的命令行也不用它的 MCP server，但这些依赖照样进二进制。如果只想要存储和检索，可以只依赖 `mempal-store-sqlite`（依赖表干净：rusqlite + sqlite-vec + serde + sha2），但那样 distill / gate / promote / context / brief 全部要自己重写——等于回到自研，方案就不成立了。**结论：接受 `mempal-runtime` 的依赖体积。** 具体增量需要实测，不在提案里编数字。

## 会被删掉的代码和能力

`src-tauri/src/memory_*.rs` 现在是 29 个文件、19171 行（含 6279 行测试）。按新模型，下列内容整体退场：

| 文件 / 能力 | 原因 |
|---|---|
| `memory_inbox.rs`、`memory_working.rs`、`memory_projection.rs` | 概念被裁决删除 |
| `memory_storage_sqlite.rs`、`memory_storage_postgres.rs`、`memory_storage.rs`、`memory_storage_migration.rs` | 存储层换成 `palace.db` |
| `memory_recall.rs`、`memory_recall_engine.rs`、`memory_schema.rs`、`search_index.rs` 的记忆部分 | 检索换成上游混合检索 |
| `memory_distill.rs`、`memory_distill_worker.rs`、`memory_provider.rs` | 蒸馏从 LLM 抽取变成确定性引用聚合，不再需要 provider |

## 对外协议变更

这一条第一版写反了。第一版的非目标里写着「不迁移 MCP server，现有 `mdx-mcp` sidecar 的对外协议不变」。做不到——协议里就有被删概念的工具：

- CLI：`MemoryInboxList` / `MemoryInboxAccept` / `MemoryInboxReject` / `MemoryWorkingGet` / `MemoryWorkingSet` / `MemoryWorkingAppend`（`src-tauri/src/cli_protocol.rs:142`-`166`）。
- MCP：`memory_inbox_add` / `memory_inbox_list` / `memory_inbox_accept` / `memory_working_get`（`docs/loopx/specs/memory.md:339`）。
- 已安装到用户机器上的 agent 技能文本，明确教 agent 调这些工具（`src-tauri/src/memory_agent_setup.rs:1304`）。

修正后的口径：**sidecar 的形态不变（还是我们自己的 `mdx-mcp`，不引入上游 MCP server，不让上游工具名出现在用户的 agent 里），但工具集按新模型重画。** 删掉的工具不留别名、不做兼容垫片；已安装的技能文本靠现有的 `memory_agent_repair` 重写一遍。升级后没有重跑修复的用户，其 agent 会调到不存在的工具——这是一次明确的破坏性变更，需要在发布说明里写清楚，并让面板在检测到旧技能文本时提示重装。

## 旧数据处置：不做 schema 迁移

第一版把「字段对不上」列为最大未知。裁决之后这个未知消失了，因为不做字段映射。

旧数据的形态帮了大忙：它本来就是 Markdown 文件，而 mempal 的 ingest 正好吃文件，并把 `source_file` 作为出处存下来。所以：

1. **不动旧目录。** `<workspace>/memory/**` 原地保留、只读。回退 = 换回旧版本应用，数据还在原处。
2. **提供一次性的显式导入**：把 `memory/memories/**.md` 和 `memory/threads/**.md` 当普通文件逐个 ingest 成 evidence（`ingest/mod.rs:194`），wing 取该工作区。按内容哈希去重，重复执行幂等。
3. **不导入 `memory/inbox/**`**——它们是没被确认过的自动产物，裁决已经说了抛弃。
4. **不导入 `memory/working.md`**——易失内容，不该沉淀。
5. **导入结果是证据，不是结论。** 旧的「长期记忆」进来之后在素材层，要重新出现在 agent 的上下文里，得走一次 distill + promote。这是这次换模型最直接的用户可感代价，导入后的报告要把这句话说清楚，并给出「哪些条目值得优先提升」的清单。

## 边界场景

| 场景 | 处理 |
|---|---|
| 用户从不启用记忆 | 不建库、不下模型、不发请求；成本只有二进制体积 |
| 首次启用但离线 | 明确报错：需要一次联网下载嵌入模型。不能降级成「只用关键词」，见「已决问题」 |
| 下载中途断网 | 不留半个模型：下到临时目录，三件文件齐全再原子移入 |
| 模型目录被手动删除 | 下次使用重新走下载流程，不崩 |
| `~/.mdx/memory/` 不可写 | 记忆整体报错并保持关闭，编辑器不受影响 |
| 多个窗口同时写 | 现在是全局单库，并发面比过去大。上游有 per-source 咨询锁（Unix 有效，Windows 是空实现），详细设计里必须确认多窗口 + sidecar 三方并发的实际保证 |
| 工作区改名或移动 | wing 不自动跟随；需要显式重新绑定，否则同项目分裂成两个 wing |
| 用户本机已装 mempal 命令行 | 两套库互不干扰；不共享，不读 `~/.mempal/` |
| 候选结论一直凑不齐证据 | 永远停在 candidate，不进上下文。这是设计意图，不是 bug；界面要让「为什么提不上去」一眼可见（gate 报告已经给了 reasons） |
| 上游 breaking change | 锁在 `Cargo.lock`，升级是显式动作，跟着上游 CHANGELOG 走 |
| 旧数据导入到一半失败 | 已导入的 evidence 保留（幂等，重跑即可续），旧目录未动，报告失败文件清单 |

## 已决问题

**PostgreSQL 后端：删。**（2026-08-17 裁决）`memory_storage_postgres.rs`（1143 行）、`memory_storage_migration.rs`、设置页里的「迁移预检 / 开始迁移」两步流程一起下线，记忆只有 SQLite 一个后端。副作用要认账：多机共享和团队共享在新模型里没有替代品，只剩导出／导入。

**提升门禁：系统自动挂证据，人一键采纳。**（2026-08-17 裁决）见「待确认 → 提升门禁」一节的流程与代价。

**嵌入模型：接受首次联网下载。**（2026-08-17 裁决）第一版设想「如果 BM25 够用就完全不引入 `mempal-embed`」，这条退路不存在——ingest 无条件调用 `embedder.embed()`，失败即整个写入失败（`ingest/mod.rs:351`）。`Embedder` 是公开 trait、只有三个方法（`mempal-embed/src/lib.rs:101`），我们能自己实现一个假的，但那会往向量表里写无意义向量、污染 RRF 融合后的排序，属于没有需求要求的降级模式，不做。定下来的行为：采用 model2vec，首次需要时由用户显式确认后下载；模型不可用时记忆写入整体判为不可用并明确报错，不降级、不静默。

## 待决问题

1. **界面词汇。** 本提案定的是「素材 / 结论」两个词，分级不暴露。如果你更想要别的说法（比如「材料 / 沉淀」），现在改成本最低。
3. **模型体积。** `potion-multilingual-128M` 的实际下载体积需实测确认（上游 README 与 CLAUDE.md 对维度的说法不一致，一处写 1024d 一处写 256d，不采信任何一处）。若过大，降级到 `potion-base-8M` 是否可接受。
4. **Phase-2 knowledge card 用不用。** 上游有比 knowledge drawer 更完整的一套卡片模型（独立表、按角色分类的证据链接、append-only 审计），但上游自己还没把它设为默认检索源。建议：第一期只用 knowledge drawer，卡片留给后续，避免同时押注两套上游尚未收敛的模型。

## 详细设计交接

阻塞详细设计的三个决定已经在 2026-08-17 裁决完毕（见「已决问题」）。剩下的待决项都不改变结构，可以在详细设计阶段随时定。

以下作为约束固定：

- 依赖 crates.io 的 `mempal-runtime` + `mempal-store-sqlite`（+ `mempal-embed`），不 fork、不 vendor、不改上游。
- 记忆模型按证据／知识两层重做；inbox、working context、projection 不保留、不映射、不做兼容垫片。
- 数据 `~/.mdx/memory/palace.db` 全局单库，按 wing 区分工作区；模型 `~/.mdx/models/`；均经我们自己的 home 解析函数。
- 构建产物不含模型；下载由用户显式确认；模型不可用时记忆写入 fail fast，不降级。
- 只有 SQLite 一个后端；PostgreSQL 后端与存储迁移界面一并删除。
- 提升走「自动挂支持证据 + 采纳时写入人工确认作为验证证据」，不批量采纳，gate 失败原样显示 reasons。
- 旧数据不迁移 schema，只提供一次性显式导入为证据；旧目录原地只读保留。
- 对外协议是一次明确的破坏性变更：删掉的工具不留别名，靠技能修复重装。
- 产品界面不出现上游名称；分级词汇不上界面。
- 不做双后端共存。
