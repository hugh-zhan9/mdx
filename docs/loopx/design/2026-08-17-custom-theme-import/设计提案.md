# 自定义主题以「变量白名单」导入，而不是执行用户的 CSS

Author(s): Claude (与 hugh-zhan9 讨论)
Last updated: 2026-08-17
Status: Draft
Discussion: 不涉及
Source requirements: 2026-08-17 会话中的口头需求——「没有像 ColaMD 一样的主题」，并明确选择「主题影响整个应用」「同时支持导入」「macOS 原生精致感」
Support lenses: architecture-designer（安全边界、失败模式、可运维性）

## 摘要

我们支持从 `~/.mdx/themes/*.css` 导入用户主题，但**不把用户的 CSS 交给浏览器执行**。Rust 侧读出文件文本，前端只从中提取一份白名单内的 CSS 自定义属性，再由我们自己生成一条 `[data-theme="user:<id>"] { … }` 规则。用户 CSS 里的选择器、`@import`、`url()` 一概不会进入页面。

由此得到的核心承诺是：**一个主题永远只能改变颜色、字体和少量尺寸，不能改变布局、不能遮挡界面、不能依赖编辑器的内部结构**。代价是表达力明确弱于 ColaMD——用户无法像在 ColaMD 里那样写 `#editor .ProseMirror h1 { border-bottom: none }`。我们认为这个代价值得付，理由见「理由与取舍」。

公开契约用 MDX 自己的变量名（`--mdx-theme-*`），不暴露 daisyUI 的内部变量名。

## 背景与动机

用户的原话是「他的 UI 太丑了，另外也没有像 ColaMD 一样的主题」。ColaMD 的做法有据可查——本仓库 `ref/ColaMD/themes/` 下有它全部 12 个主题：每个是 34–50 行的 CSS，定义一组变量（`--bg-color`、`--text-color`、`--code-bg` 等），再补几条直接选择器微调，用户可以把 `.css` 放进 `~/.colamd/themes/` 或用「Theme > Import Theme」导入。

我们目前的处境有四个既成事实，它们共同决定了方案形状：

1. **换肤的基础设施已经就绪。** 全应用 559 处颜色全部走 daisyUI 语义类，硬编码色值为 0；本次会话已落地 6 个内置主题、`data-theme` + `data-mdx-appearance` 双属性机制，以及设置面板里的主题选择器。
2. **`~/.mdx/` 已经是既有的用户级目录约定。** `src-tauri/src/assets.rs:612` 的 `mdx_home_dir()` 已被 assets 与 drafts 使用，主题目录不需要新立门户。
3. **前端没有任何文件系统权限。** `src-tauri/capabilities/default.json` 只授予 `core:default`、若干 window 权限和 `dialog:default`，没有 `fs:*`。本项目的架构是文件 IO 全部经 Rust command。
4. **`docs/loopx/specs/editor.md:23` 已经禁止了 ColaMD 那种写法。** 原文要求「Milkdown context、ProseMirror positions and plugin keys、CodeMirror views、**third-party theme classes**、and implementation-private DOM must not cross that boundary」。ColaMD 主题依赖 `.ProseMirror` 这类实现私有类名，在本仓库是既有 spec 明令禁止的。

第 4 点是本提案与 ColaMD 分道扬镳的直接原因，不是我们的偏好。

另有一条本次会话刚付过学费的证据：编辑器样式表原本挂在已删除的自研 kernel 的 DOM 契约上（`[data-mdx-node-type="heading"]` 等 66 处），kernel 一删，全部块级样式静默失效，而 1449 个测试全绿。**样式依赖 DOM 结构是会悄悄烂掉的**，这正是我们不愿意让用户主题也依赖 DOM 结构的经验来源。

## 目标与非目标

### 目标

- 用户把一个 `.css` 文件放进 `~/.mdx/themes/`，重启或点刷新后，它出现在设置面板的主题列表里，可选中、可持久。
- 主题影响整个应用（工具栏、文件树、标签页、大纲、编辑器），与内置主题同等地位。
- 主题文件损坏、非法、被删除，都不会让应用失去可用外观。
- 契约稳定：今天写的主题文件，在编辑器实现更换后仍然有效。

### 非目标

- **不做 ColaMD 级别的表达力。** 不支持用户写选择器、伪类、媒体查询、动画、字体 `@font-face`。
- **不做主题市场、在线下载、自动更新。**
- **不做文件监听热重载。** 发现主题需要显式动作（启动或点刷新）。
- **不改内置主题的机制。** 内置主题继续由构建期的 daisyUI theme 定义承载。
- **不做主题编辑器 UI。** 用户用文本编辑器写 CSS。

## 设计方案

### 最小可用版本

一个主题文件就是一份变量声明：

```css
/* ~/.mdx/themes/kraft.css */
:root {
  --mdx-theme-name: "牛皮纸";
  --mdx-theme-appearance: light;

  --mdx-theme-bg: #f3ece1;
  --mdx-theme-text: #2f2a24;
  --mdx-theme-accent: #8a5a2b;
}
```

选择器写什么我们**不关心也不使用**——`:root`、`body`、`#editor .ProseMirror` 都一样，解析器只在整个文件文本里找 `--mdx-theme-*: <value>;` 形式的声明。这既让 ColaMD 风格的文件不至于完全报错，也让"选择器有意义"这个错觉不成立：我们在文档里明确说明选择器被忽略。

未声明的变量回落到同 appearance 的内置默认值。所以上面 3 行就是一个可用主题，不必写满。

### 公开契约：14 个变量

契约用 `--mdx-theme-*` 前缀，与内部实现变量隔开。用户写契约名，解析器映射到内部名。

| 契约变量 | 含义 | 值类型 |
|---|---|---|
| `--mdx-theme-name` | 列表里显示的名字 | 带引号字符串 |
| `--mdx-theme-appearance` | `light` 或 `dark`，**必填** | 关键字 |
| `--mdx-theme-bg` | 内容区背景 | 颜色 |
| `--mdx-theme-surface` | 侧边栏、面板背景 | 颜色 |
| `--mdx-theme-chrome` | 工具栏、标签栏背景 | 颜色 |
| `--mdx-theme-text` | 正文色 | 颜色 |
| `--mdx-theme-text-muted` | 次要文字、占位符 | 颜色 |
| `--mdx-theme-border` | 分隔线、边框 | 颜色 |
| `--mdx-theme-accent` | 主按钮、选中态 | 颜色 |
| `--mdx-theme-link` | 链接与 wikilink | 颜色 |
| `--mdx-theme-code-bg` | 行内代码与代码块背景 | 颜色 |
| `--mdx-theme-selection` | 选区背景 | 颜色 |
| `--mdx-theme-body-font` | 正文字体族 | 字体族列表 |
| `--mdx-theme-mono-font` | 等宽字体族 | 字体族列表 |

**为什么不直接暴露 daisyUI 的 `--color-base-100`：** 那会把 daisyUI 从「当前的 UI 框架选择」固化成「用户主题依赖的公开契约」。一旦有人写了主题，我们就再也不能换掉 daisyUI，除非破坏所有人的主题。契约名与内部名解耦，代价是一张映射表，收益是把框架选择留在可逆的一侧。映射表由「解析而非注入」这个决定免费提供——既然我们自己生成规则，写什么内部变量名完全由我们决定。

`--mdx-editor-max-width` 一类的尺寸变量本版**不开放**：行宽是排版决定，不是配色，开放它等于让主题改变布局。这是刻意收窄，将来可以additive 地放开。

### 解析而非注入

流程：

1. Rust command `list_user_themes()` 扫描 `~/.mdx/themes/*.css`，返回 `[{ fileName, text }]`。文件读取、路径规范化、符号链接与越界拒绝都在 Rust 侧，与 assets/drafts 用同一套 `mdx_home_dir()` 约定。
2. 前端解析器对每个文件文本，用一条正则逐个抽取 `--mdx-theme-<known>: <value>;`。**不做 CSS 语法解析**——我们不需要理解这个文件，只需要从中取出认识的键值对。
3. 每个值过校验（下节）。
4. 通过校验的键值对，生成一条规则并写入一个我们自己拥有的 `<style data-mdx-user-themes>` 元素：

```css
[data-theme="user:kraft"] {
  --color-base-100: #f3ece1;
  --color-base-content: #2f2a24;
  --color-primary: #8a5a2b;
  --mdx-content-bg: #f3ece1;
  /* … 由映射表决定 */
}
```

用户文件里的其它一切——选择器、`@media`、`@import`、注释、`url()`、非白名单变量——从不参与生成，因此不可能到达页面。

### 值校验

每个值必须整体匹配一条保守规则，否则该项被丢弃：

- **颜色**：`#rgb`/`#rrggbb`/`#rrggbbaa`、`rgb()`/`rgba()`/`hsl()`/`hsla()`（参数只含数字、`%`、`.`、`,`、空格、`/`）、或 CSS 命名颜色。
- **关键字**：`light` | `dark`（仅 appearance）。
- **字符串**：`--mdx-theme-name` 只接受一对引号包裹、不含引号与反斜杠的文本，长度 ≤ 40。
- **字体族**：只含字母、数字、空格、连字符、逗号、点和引号，长度 ≤ 200。

一律禁止的字符：`{` `}` `;`（分隔符之外）、`@`、`\`、`(` 除上述函数形式、`<`、`>`，以及 `url`、`javascript`、`expression`、`image-set`、`element` 这些词。单值长度上限 200，单文件上限 64 KiB。

这里的立场是**白名单而非黑名单**：不匹配即丢弃，而不是"过滤掉危险部分"。CSS 值的攻击面（`url()` 外联、`image-set()`、自定义属性里藏 `}` 逃逸出规则块）不适合用黑名单收。

### 明暗必须显式声明

`--mdx-theme-appearance` 缺失或非 `light`/`dark`，则**整个主题被拒绝**，在设置里以「无法加载」列出并说明原因。

不从背景色亮度推断。滚动条、表单控件、代码高亮配色、macOS 原生标题栏四处都依赖这个答案（本次会话刚把它们统一到 `data-mdx-appearance`），推断错一次就是四处同时错，而错误的表现（深色主题配浅色滚动条）比"这个主题没加载，因为缺一行声明"难诊断得多。这是唯一一个我们选择**整体拒绝**而非"忽略该项"的字段。

### 部分非法：忽略该项，但要让用户看见

除 appearance 外，单个变量非法只丢弃该项，其余生效。设置面板在该主题下显示「已忽略 N 项」并可展开看是哪几个键、为什么。

理由：一个笔误废掉整个主题，对手写 CSS 的用户是很差的体验；但静默忽略又会让人对着一个"没生效"的颜色反复怀疑自己。两者之间，我们选择生效 + 明示。

### 加载时机与首帧

自定义主题的值来自异步文件读取，而设置 `data-theme` 的脚本在注水前同步运行（`app/layout.tsx`）。两者无法在首帧汇合，因此**选中自定义主题的用户会看到一帧内置主题**——深色用户会看到白闪，这在实际使用中相当刺眼。

我们的处理：**注水前脚本从 localStorage 读上一次解析出的变量并直接应用**。缓存由注水后的真实读取覆盖纠正，所以缓存过期的后果是"一帧旧颜色"，而不是错误状态。缓存里只有我们自己生成的、已过校验的键值对，不是用户文件原文。

代价是多一处缓存及其失效逻辑。不做的代价是每次冷启动闪一次，我们判断后者更不可接受。

### 命名与冲突

自定义主题 id 一律带 `user:` 前缀（`user:<文件名去扩展名>`），与内置主题 id 空间不相交。两个文件重名不可能（同目录），大小写不同的同名文件在 macOS 默认不区分大小写的卷上也不可能同时存在。

| architecture-designer | 引入了一条从用户文件到渲染页面的新数据通路，涉及安全边界与失败模式 | 系统边界与所有权（文件 IO 归 Rust、解析与生成归前端、渲染归浏览器）；失败模式表（见下）；降级行为（拒绝 / 忽略项 / 回落系统主题）；访问控制（只读、限定目录、不执行）；可观测性（设置面板暴露每个主题的加载结果与忽略项）；可运维成本（无后台进程、无监听、无网络） | 采纳。一项被这条视角改掉：最初考虑"解析失败就静默跳过该文件"，失败模式检查表明用户会得到一个"主题凭空消失"的不可诊断状态，改为在列表中列出并说明原因 |

## 边界场景

| 场景 | 处理 |
|---|---|
| `~/.mdx/themes/` 不存在 | 不是错误。列表为空，不创建目录，不报警 |
| 目录存在但为空 | 列表为空，设置里显示指引（目录路径 + 一个最小示例） |
| 文件不是 UTF-8 / 是二进制 | Rust 侧读取失败，该文件以「无法读取」列出 |
| 文件超过 64 KiB | 拒绝该文件并说明上限。上限存在的意义是这不是一个能放整套 CSS 框架的地方 |
| 文件里没有任何认识的变量（例如原封不动的 ColaMD 主题） | 拒绝，理由写明「未找到 `--mdx-theme-*` 声明」，并指向契约文档。这是最可能发生的用户错误，值得一条专门的提示 |
| 缺 `--mdx-theme-appearance` | 整体拒绝（见上） |
| 单个颜色值非法 | 忽略该项，其余生效，设置里计数并可展开 |
| 值里试图逃逸规则块（`#fff; } body { display:none`） | 不匹配颜色规则，整项丢弃。即便匹配，生成规则时值是我们逐项写入的，不是字符串拼接原文 |
| 值里含 `url(...)` 外联 | 被禁止词与括号规则拒绝。杜绝主题文件成为一个对外发起请求的渠道 |
| 已选中的主题文件被删除 | `resolveThemePreference()` 已有行为：未知 id 回落到「跟随系统」。本次仅需让它同时认识已加载的自定义主题 id |
| 已选中的主题文件被改坏 | 回落到「跟随系统」，并在设置里保留该主题的失败原因 |
| 重复点「刷新」 | 幂等：重新扫描、重新生成整个 `<style>` 内容，不追加 |
| 刷新时正在使用的主题消失了 | 与"被删除"同路径 |
| 两个窗口同时打开 | 每个窗口各自扫描、各自生成 `<style>`。主题偏好经 localStorage + 既有的 `mdx-theme-change` 事件同步，与内置主题现状一致 |
| 内置主题、CLI、发布导出、PDF 导出行为 | 不变。主题只改 CSS 变量；PDF 导出走只读 publishing 通路，本提案不接触 |
| 明暗切换跟随系统时选了自定义主题 | 「跟随系统」与「具体主题」互斥，与内置主题同一模型：选了具体主题就不再跟随系统 |

## 理由与取舍

| 备选方案 | 为什么不选 |
|---|---|
| 直接把用户 CSS 注入 `<style>`（ColaMD 做法） | 三个具体后果：① 违反 `editor.md:23`——用户会依赖 `.ProseMirror` 等私有类，而我们本次会话刚因为样式依赖已删除的 DOM 契约而全线失效；② 一条 `display:none` 或 `position:fixed` 就能遮挡或隐藏 UI，包括设置入口本身，用户会陷入无法改回来的状态；③ `url()` 让主题文件成为对外请求渠道。CSP 当前为 `null`，没有第二道防线 |
| 注入原文，但用 CSP 限制 `url()` | 只堵住第三个后果。遮挡 UI 和依赖私有 DOM 都还在。且给整个应用引入 CSP 是一次独立的、影响面更大的改动 |
| 把编辑器放进 iframe 或 Shadow DOM 隔离主题 | 隔离的是"编辑器不受外界影响"，而我们要的恰恰相反——主题必须能改整个应用。且 iframe 会切断选区、拖放、输入法与 CLI 定位，代价与收益完全不匹配 |
| 主题用 JSON / TOML 而非 CSS | 更安全也更好校验，但用户明确要「像 ColaMD 一样」，ColaMD 生态里流传的是 `.css` 文件。用 CSS 语法承载变量声明，让一个 ColaMD 主题至少"看起来像能用"，迁移时只需改变量名而不是换文件格式 |
| 暴露 daisyUI 变量名作为契约 | 把当前的 UI 框架选择固化成不可逆的公开承诺。详见「公开契约」一节 |
| 支持文件监听、改文件即时生效 | 需要常驻 watcher 与失效协议，而这是一个用户一年改几次的设置。显式刷新的成本是一次点击 |
| 允许主题设置尺寸（行宽、圆角、间距） | 那是布局而非配色，会让"主题不能改变布局"这条承诺失效，也会让排版回归成为主题的责任。可以将来 additive 放开，收回则是破坏性的 |

## 兼容性

**纯增量，不破坏任何现有行为。**

- 未放置任何主题文件的用户，看到的与今天完全一致。
- `themePreference` 的存储格式不变（仍是一个字符串），只是取值空间增加了 `user:*`。早先版本存的 `light`/`dark`/`system` 继续有效——本次会话已加测试钉住这一点。
- 一个存了 `user:x` 的偏好被降级到不认识它的旧版本打开：旧版 `resolveThemePreference()` 不认识该 id，回落「跟随系统」。不会崩，不会白屏。
- 不新增 Tauri 权限（走新的 Rust command，而非开放 `fs:*`），不引入依赖，不改 CSP，不改 Markdown 持久化格式。

**将来会受约束的地方：** 14 个契约变量名一旦发布即为公开承诺。新增变量是 additive 的；改名或删除是破坏性的，需要走 `spec`。

## 运行与安全影响

安全立场一句话：**用户主题是数据，不是代码。** 它经过解析、校验、重新生成，从不被执行。

| 失败模式 | 触发 | 影响 | 检测 | 恢复 | Owner |
|---|---|---|---|---|---|
| 主题目录不可读（权限） | 权限变更、iCloud 同步中 | 自定义主题全部不可用 | 设置面板显示读取失败与路径 | 内置主题不受影响，应用照常 | 用户 |
| 主题文件语法错乱 | 手写笔误 | 该主题不可用或部分项被忽略 | 设置面板列出原因与忽略计数 | 改文件后点刷新 | 用户 |
| 生成的规则本身有误（我们的 bug） | 映射表错误 | 某些界面颜色不对 | 视觉可见；单测覆盖映射表 | 回落内置主题 | 我们 |
| localStorage 缓存与文件不一致 | 用户改了文件但未重启 | 首帧一帧旧颜色 | 注水后自动纠正 | 无需动作 | 我们 |
| 主题把前景背景设成同色 | 用户自己配错 | 该主题下文字不可读 | 用户可见 | 换主题即可；不做对比度强制 | 用户 |

对比度不做强制校验也不做自动修正：那是审美与可读性的判断，一旦我们改写用户的颜色，用户就无法解释屏幕上看到的东西。**我们只保证不可读的主题可以被换掉，不保证不存在不可读的主题。**

运维面：无后台进程、无网络、无监听、无定时任务。新增磁盘读取仅在启动与显式刷新时发生，读的是用户自己目录下的小文件。

## 实现与过渡

四段，顺序有依赖：

1. **契约与映射表**（前端，纯函数 + 单测）：14 个契约变量到内部变量的映射，值校验，规则生成。这一段不碰 UI 也不碰 Rust，可以完全用测试驱动。
2. **Rust command**：`list_user_themes()` 读目录与文件，复用 `mdx_home_dir()`。含越界与符号链接拒绝的测试。
3. **接入与 UI**：主题注册表合并内置与用户主题；设置面板列出用户主题、失败原因、忽略计数、目录路径、刷新按钮、最小示例。
4. **首帧缓存**：注水前脚本读 localStorage 缓存。放在最后，因为它是优化而非功能，前三段完成即可用。

第 1 段之前需要先落地一份**契约文档**（`docs/loopx/specs/theme.md`），因为它是公开承诺，应当与代码同源可查。

## 待决问题

1. **契约变量集是否就这 14 个？** 我按"够写出 ColaMD 那 12 个主题的等效效果"选的，但 ColaMD 的 `--highlight-bg`（高亮/标记背景）和 `--table-header-bg`（表头背景）我没纳入——前者本产品尚无对应语义，后者我认为可由 `--mdx-theme-surface` 承担。若你希望逐一对齐 ColaMD 的变量集，需要在详细设计前确认。**这一项阻塞详细设计**，因为契约一旦发布不可逆。
2. **是否需要「导入」按钮（文件选择器 → 复制进 `~/.mdx/themes/`）**，还是只支持用户自己把文件放进目录？项目已有 `dialog:default` 权限，做得起。ColaMD 两条路都提供。**不阻塞**——可以后续 additive 增加。
3. 主题文件是否需要支持一个 `--mdx-theme-author` 之类的元数据？**不阻塞**，倾向不做。

## 详细设计交接

**建议先评审本提案，暂不进入详细设计**，因为待决问题 1 直接决定公开契约的内容，而契约不可逆。

评审通过后，详细设计须把以下决定作为固定约束，不再重开：

- 用户 CSS 不被执行；只提取白名单变量并由我们生成规则。
- 契约变量用 `--mdx-theme-*` 前缀，不暴露 daisyUI 内部变量名。
- `--mdx-theme-appearance` 必填，缺失即整体拒绝，不做亮度推断。
- 除 appearance 外，单项非法只忽略该项，且必须对用户可见。
- 主题不得改变布局尺寸；本版不开放行宽等尺寸变量。
- 文件 IO 走新的 Rust command，不开放前端 `fs:*` 权限。
- 自定义主题 id 带 `user:` 前缀。
- 纯增量，`themePreference` 存储格式不变。

| ColaMD | MDX 契约 | 备注 |
|---|---|---|
| `--bg-color` | `--mdx-theme-bg` | |
| `--text-color` | `--mdx-theme-text` | |
| `--text-muted` | `--mdx-theme-text-muted` | |
| `--border-color` | `--mdx-theme-border` | |
| `--link-color` | `--mdx-theme-link` | |
