# P-007 — `D-015` performance measurement procedure

Operational procedure for the `AC-014` performance gate. It is written for the
person who takes the measurement on real hardware, and it is deliberately
explicit about what a machine cannot decide for itself.

Contract: `D-015`, section 9.2 of `需求设计文档.md`. Thresholds: `AC-014`.
Test case: `TC-013`.

---

## 0. What this procedure will not do

**It will not tell you a threshold is met unless the run is admissible.** The
verifier refuses — non-zero exit, no number reported as a pass — when the build
is not release-like, when the fixtures are not the pinned bytes, when the sample
count is short, when machine metadata is missing, or when the WebView could not
take one of the measurements at all. Those refusals are proven, not asserted;
see §7.

**Two of the measurements cannot be automated, and the reason is not
convenience.**

- **Input latency** is anchored on `beforeinput`. Only a real key event produces
  one. `document.execCommand("insertText")` inserts the character and fires
  `input` but not `beforeinput` — verified in Chromium 151 against this very
  harness: the text landed, a capture-phase `beforeinput` listener on the editor
  container saw nothing, and all 44 scripted samples in the smoke run recorded
  `no-beforeinput-event`. Anchoring on `input` starts the clock *after* the DOM
  has already changed, which is a shorter interval than the contract defines, so
  the harness records those samples with `driver: "execCommand"` and the verifier
  never counts them.
- **IME commit latency** needs a real input method. A synthetic
  `CompositionEvent` does not put ProseMirror into a composing state, so a number
  taken from one would describe the harness rather than the IME.

Both are therefore *attended*: the harness records them continuously while a
person types, and shows a live count of how many valid samples each fixture has.

## 1. The fixtures

Two deterministic mixed-syntax documents, generated rather than committed.

| id | bytes | seed |
| --- | --- | --- |
| `mixed-100kib` | 102 400 | `mdx-p007-100kib` |
| `mixed-1mib` | 1 048 576 | `mdx-p007-1mib` |

The generator (`scripts/editor-perf-fixture.mjs`) is pure — seeded PRNG, no
clock, no environment reads — so the same seed produces the same bytes in Node
and in the app's WebView. That is what lets a measurement be tied to exact
bytes: the harness generates the fixture in-page and records its SHA-256, and
the verifier compares that against the committed pin
(`P-007-fixture-checksums.json`).

Both fixtures carry frontmatter (YAML and TOML), GitHub callouts including
unknown kinds, mermaid, inline and block math, footnote calls with definitions,
wikilinks with and without aliases, raw block and inline HTML, unknown `:::`
container directives, GFM tables, nested and task lists, fenced code including a
nested fence, emoji, combining characters and CJK — in the proportions a real
document of that size would carry, not one construct repeated.

```
npm run fixtures:editor:perf          # write to artifacts/editor-perf/fixtures/ and check the pin
npm run fixtures:editor:perf:check    # check the pin without writing
```

Both exit non-zero if the generated bytes drift from the pin or if any syntax
family disappears from the mix. `packages/mdx-editor/test/editor-perf-fixture.test.ts`
additionally proves the fixtures round-trip through the real Milkdown syntax
layer byte for byte, which is what makes them a fair measurement subject: a
fixture the editor silently rewrites is not the fixture that was checksummed.

## 2. The machine

`D-015` fixes the baseline at Apple M5 10-core / 16 GB / macOS 26.4, or an Apple
Silicon Mac no slower.

1. Close unrelated heavy applications. Browsers with many tabs, containers,
   builds, and anything indexing.
2. Connect mains power.
3. Let the machine settle — check `pmset -g therm` reports no thermal warning.

---

## 3. The build

The measurement runs inside a release-like Tauri build with release web assets
and no DevTools. `next dev` in a desktop browser is **not** that build and the
harness stamps such a run as disqualified.

```
git status --porcelain          # must be empty; the recorded commit must describe the build
npm run qualify:editor:build    # NEXT_PUBLIC_MDX_MILKDOWN_QUALIFICATION=1 + commit stamp + tauri build
npm run install:local
```

`qualify:editor:build` sets:

- `NEXT_PUBLIC_MDX_MILKDOWN_QUALIFICATION=1` — the same build-time flag
  `features/editor/lib/editor-surface-qualification.ts` already uses. Without it
  the harness route renders an inert refusal and the qualification surface is
  unreachable. Nothing in navigation or settings links to either; the audit in
  §6 checks that on every run.
- `NEXT_PUBLIC_MDX_BUILD_COMMIT` — baked so the artifact carries the commit. The
  harness disqualifies a run where this is absent.

Do not open DevTools at any point during the run.

## 4. Collect the environment metadata

On the measuring machine, immediately before the run:

```
mkdir -p artifacts/editor-perf
npm run qualify:editor:environment > artifacts/editor-perf/environment.json
```

Then open the file and fill in the `attestations` block. The verifier refuses
while any of these is `null`:

| field | meaning |
| --- | --- |
| `devToolsClosed` | DevTools were not opened at any point during the run |
| `releaseBuild` | the build under test came from `npm run qualify:editor:build` |
| `unrelatedAppsClosed` | unrelated heavy applications were closed first |
| `operator` | who took the measurement |
| `hardwareJustification` | required **only** if the chip is below M5; name the ruling that allows it |

The script records the machine model, chip, cores, RAM, macOS product and build
version, WebKit framework version, power source, thermal state, load average,
the ten heaviest processes, the app commit, and whether the working tree was
clean. Anything a command could not produce is recorded as `null` and listed in
`unavailable` — never guessed.

## 5. Take the measurement

Launch the installed app and navigate the window to `/mdx-editor-qualification`.

### 5.1 Scripted phases

Press **Run scripted protocol**. It walks both fixtures and measures:

- **First editable** — five cold mounts per fixture, each from the adapter mount
  mark to the first animation frame after `onReady`. The mount mark is taken in
  the render that creates the adapter element, the last moment before React
  commits it and the adapter's own build effect runs; that is as close to the
  adapter's mount as a caller can stand without reaching inside the package. The
  verifier evaluates the **slowest** of the five against the threshold.
- **Mode switch** — 3 warm-up switches each way (recorded, discarded), then 20
  in each direction, each timed from the `setMode` call to the first animation
  frame after the resulting `onReady`. The verifier reports the slowest.
- **Long task** — a `PerformanceObserver` on `longtask` over 30 seconds of
  continuous scrolling of the editor's own scroll container.
- **Scripted insert** — 200 `execCommand` insertions per fixture, recorded as
  `driver: "execCommand"` and **not counted**. Keep them: they are a cheap
  regression signal and they document what the scripted path can and cannot see.

> **Known blocker — check this first.** The Long Tasks API is not implemented in
> WebKit at the time of writing. If it is missing from the WebView, the harness
> records `longTaskObserverSupported: false`, adds a note, and the verifier
> refuses the long-task threshold rather than substituting the frame-gap figure
> it also records. Substituting it would change the measurement definition,
> which `D-015` reserves for a `spec` ruling. If the refusal fires, stop and
> take that decision — do not report a long-task pass from the frame gaps.
>
> The phase itself is known to work where the API exists: in the Chromium smoke
> run it captured 27 long-task entries over 3 seconds of scrolling the 1 MiB
> fixture, the worst 668 ms. Whether WKWebView produces any is the open
> question, and the harness answers it on the device rather than assuming.

### 5.2 Attended phases

For each fixture in turn, select it with the fixture buttons, click into the
editor, and:

1. **Type 200 characters** with a plain keyboard layout. Ordinary prose is fine;
   type into body text, not into a code fence. The header shows
   `typed n/200` for the selected fixture and the running p95.
2. **Commit 200 IME compositions.** Switch to Simplified Chinese Pinyin, type a
   syllable, press Space or a candidate number to commit, repeat. Then do the
   same with Japanese (Romaji) input. Split the 200 roughly evenly between the
   two. The header shows `IME n/200`.

Both counters only ever advance for real key events, so there is no way to reach
the target with a script.

The IME phase is where the highest-risk gap lives: the new editor package
contains **no IME composition handling at all**, while the legacy surface guards
composition explicitly. Run
`P-007-macos-manual-checklist.md` §1 before spending time on the sample count —
if composition is broken, the latency number is not the interesting result.

### 5.3 Export

Press **Build artifact JSON**, then **Copy artifact JSON**, and paste into
`artifacts/editor-perf/artifact.json`. The artifact carries every sample — valid
and invalid, with a reason for each invalid one — the long-task entries, the
frame gaps, the fixture checksums and syntax profiles, and the WebView
environment. It is not a summary; the summary is computed from it by the
verifier and can be recomputed by anyone.

## 6. Verify

```
npm run audit:editor:boundaries
npm run fixtures:editor:perf:check
npm run qualify:editor:verify -- artifacts/editor-perf/artifact.json \
    --environment artifacts/editor-perf/environment.json
```

The verifier prints one line per metric with its threshold and its median, and
exits 0 only if every threshold is met on an admissible run. The p95 is computed
by nearest rank over the valid samples. No mean is computed anywhere in the
script.

## 7. What the verifier refuses, and the proof it does

Each of the following was proven by mutating one field of a synthetic
*admissible* artifact and confirming a non-zero exit with a stated reason:

| refusal | proven by |
| --- | --- |
| no `--environment` file | omitting the flag |
| run not qualifying | `qualifying: false` with a disqualification |
| unknown artifact schema | schema bumped to `/99` |
| fixture checksum drift | one `sha256` replaced |
| fewer than 200 input samples | deleting a third of them |
| only scripted input samples | every input sample retagged `driver: "execCommand"` |
| fewer than 200 IME samples | deleting them |
| fewer than 20 mode switches in a direction | deleting them |
| no Long Tasks API | `longTaskObserverSupported: false` |
| input p95 over 50 ms | durations raised to 90 ms |
| first editable over its threshold | 100 KiB raised to 640 ms |
| long task over 100 ms | one entry raised to 180 ms |
| battery power | `power.source: "battery"` |
| dirty working tree | `workingTreeClean: false` |
| missing attestation | `devToolsClosed: null` |
| no operator | `operator: null` |
| no macOS version | `productVersion: ""` |
| truncated commit | `commit: "abc123"` |
| non-Apple-Silicon machine | Intel chip string |
| chip below the M5 baseline with no ruling | `Apple M2` |
| RAM below 16 GiB | `memoryGiB: 8` |
| long-task observation inconsistent with the recorded frame gaps | the real smoke artifact from before the `takeRecords` fix: a 275 ms frame gap with zero long-task entries |

The last row is not hypothetical. The first version of the scroll phase called
`observer.disconnect()` as soon as the loop ended, which discarded the long-task
entries still queued for delivery: the run reported **zero** long tasks
alongside a recorded 275 ms frame gap, and would have been printed as
`0.00 ms (< 100 ms) ok`. Two changes came out of it — the harness now drains
`takeRecords()` after a five-frame settle before disconnecting, and the verifier
refuses whenever a frame gap at or above the threshold coexists with no
long-task entry at all. After the fix the same smoke run captured 27 entries,
the worst 668 ms, and the verifier reported it as a threshold failure.

## 8. Development smoke run

```
npm run qualify:editor:smoke
```

Starts `next dev` with the flag, drives the protocol in Chromium with reduced
counts, and writes `artifacts/editor-perf/dev-smoke-artifact.json`. It exercises
the whole protocol in a few minutes and is **not** a qualifying measurement: the
artifact stamps itself with the development build, the browser runtime, the
missing commit and the reduced counts, and feeding it to the verifier is
expected to exit non-zero. That refusal is the check that the gate works.
